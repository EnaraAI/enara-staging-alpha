### Application cumulative cap (G11a: PASS in code; G11b: BLOCKED in configuration)

| Requirement | Implementation (`services/aiBudget.ts`, `aiGateway.ts`, `stagingGuard.ts`) | Tests |
|---|---|---|
| One cumulative cap across every feature and school | `reserveTestSpend`: an atomic conditional `$inc` on `budget_counters/test_spend:<id>`, reserved **before** pauses and school budgets, for every attempt | `p14_2GradingTestSpend` 8; `p14_3TestSpendEnforcement` concurrency |
| Every provider | Every served call goes through `reserveAttempt`: Anthropic (`meteredMessage`/`meteredStream`/`trackAiCall`/`askForJson`), ElevenLabs (`meteredSpeech`/`meteredCall`), Anam session, orchestrator chat, ingestion engine. Unmetered SDK sites exist only in offline `src/scripts/*`. The guard refuses to start staging when any paid-provider variable is set without cap and id | `p14_3StagingStartup` (6 paid paths) |
| `ai_grading` | Reserves against the same counter first; refused at the cap with no provider call and no ledger row | `p14_2GradingTestSpend` 7, 8b; `p14_3` pause cases |
| Retries | SDK retries off (`maxRetries: 0`) at every client; each gateway retry is a separate attempt with its own reservation; failed attempts are kept whole | `p14_3` retries, retries past the cap |
| Concurrency | A single atomic document update across all serverless instances; 24 concurrent requests with room for 5 → exactly 5 | `p14_3` concurrency |
| Fallback paths | The tutor's server-side model fallback is priced `anyModel` (the most expensive catalogued model). Tutor ↔ orchestrator fallback goes through metered calls (the orchestrator is not configured). A call with no bound (unpriced model, tutor with a PDF, Anam, orchestrator) is **refused** under the cap unless the school has a configured ceiling | `p14_2` unbounded refusal; `tutorFallback` |
| Failure of the cap's own store | Fails closed for every feature (`AI_BUDGET_UNAVAILABLE`) | `p14_2` 9b |
| Reused attempt key | Refused (P14.3 D3) | `p14_3` replays |

**Residual limits:**
1. **The cap counts reserved upper bounds.** One call that bills more than its bound could pass the cap by that call's difference. The bound counts input as at least one token per byte plus 1,024 at the highest input rate, plus output at `maxTokens` × the output rate, so an overshoot is not expected. Even so: set the app cap below the provider cap (recommended **$4.50**).
2. **The guard checks that the cap is present, not that it is ≤ $5**, so the operator must read the value back (G11b). *Optional code hardening, not done here:* refuse `AI_TEST_SPEND_CAP_USD > 5` in staging.
3. **Use a fresh `AI_TEST_SPEND_ID`** for the test window (e.g. `p14-live-1`); reusing an id continues its counter.
