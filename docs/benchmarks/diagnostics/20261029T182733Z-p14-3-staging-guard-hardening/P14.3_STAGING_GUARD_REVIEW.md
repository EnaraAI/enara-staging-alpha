## Phase 1: review of the P14.2 implementation

Each answer comes from reading the code path, not only from test results.

| # | Question | Finding | Classification |
|---|---|---|---|
| 1 | Does the guard run before the DB connection and migrations? | **Yes.** `vercel.ts` calls `assertStagingEntry()` and `getConfig()` (which runs `assertStagingIsolation`) at module load, before `createApp()`. `connectDB()` (connect + migrations) runs only inside the request handler. No imported module connects to a database or starts migrations at import time: the only callers are `index.ts`, `vercel.ts` and offline scripts. `openMongo()` re-checks the database name after every connect | VERIFIED_EXISTING (+ source-order test added) |
| 2 | Does invalid staging configuration reliably fail closed? | **Mostly.** Every guard problem throws at load. **Defect D1:** the guard accepted `RUN_MIGRATIONS_ON_START` case-insensitively and trimmed (`FALSE`, ` false`), but `connectDB` skipped migrations only for the exact string `false`. So `FALSE` passed the guard and migrations still ran on start | **FIXED_AND_TESTED** |
| 3 | Is the staging flag parsed and validated safely? | **Yes.** Only unset, empty, `1/true/yes` or `0/false/no` are accepted. Anything else throws in `loadConfig`. The Vercel entry additionally requires a true value | VERIFIED_EXISTING |
| 4 | Does a provider key require a valid test-spend cap in staging? | **Partly.** Only `ANTHROPIC_API_KEY` and `ELEVENLABS_API_KEY` were checked, and only the cap's presence. **Defect D2:** the other paid paths (`ANAM_API_KEY`, `ENARA_API_KEY`, `ENARA_ORCHESTRATOR_URL`, `AI_ENGINE_URL`) could be enabled in staging without a cap. Cap and id validity were already enforced by `parseTestSpend` (positive number; id pattern; both or neither) | **FIXED_AND_TESTED** |
| 5 | Does the cap cover every provider-backed feature, grading included? | **Yes.** Every served provider call goes through `reserveAttempt` → `reserveAiBudget`, and the test cap is reserved first, for every feature: Anthropic `meteredMessage`/`meteredStream`/`trackAiCall`, ElevenLabs `meteredSpeech`/`meteredCall`, Anam session, orchestrator chat, ingestion engine. The only unmetered SDK call sites (`candidateV2Live/*`) are imported only by offline `src/scripts/*`, never by the app | VERIFIED_EXISTING |
| 6 | Are reservations created and settled safely? | **Mostly.** Creation is atomic: a conditional `$inc` on one counter document. Settlement refunds a known cost and keeps an unknown cost whole. A failed settlement leaves the reservation held, and the sweep keeps it as unknown. **Defect D3:** a reused attempt key returned "reserved" without reserving. That meant (a) a replay after settlement could make a provider call with no reservation, and (b) if the school check then refused, the wrapper would release the *first* attempt's test reservation | **FIXED_AND_TESTED** |
| 7 | Can concurrent requests oversubscribe the cap? | **No.** Each reservation is a single atomic conditional update (`committedMicros ≤ cap − amount`) on one document. Upsert races are absorbed (duplicate-key ignored). Tested with 24 concurrent requests across 2 schools and 4 features at cap = 5 × bound: exactly 5 succeed | VERIFIED_EXISTING (+ test added) |
| 8 | Are provider failures, missing usage, retries and unknown cost handled conservatively? | **Yes.** SDK retries are off (`maxRetries: 0`) at every client. Each gateway retry is a new attempt with its own key and reservation. A failed attempt is settled with `null` cost (ledger `usage_unknown`), keeping the full reservation. A cancelled stream gets unknown usage. Unsettled reservations stay counted; on Vercel no cron sweeps them, so they stay counted, which over-counts | VERIFIED_EXISTING (+ tests added) |
| 9 | Can the guard be bypassed through another entry point or provider path? | **Not on Vercel.** `vercel.json` defines one function. `api/` contains only `index.js`, which requires only `dist/vercel.js`. There is no backend-level Vercel config or `backend/api/`. **Off Vercel:** `src/index.ts` (Docker/Railway `CMD node dist/index.js`) still uses the opt-in flag, because it also serves local development. Those targets are not used for P14 | VERIFIED_EXISTING for Vercel (+ test added); Railway/Docker: DEFERRED_BY_OWNER (not a P14 target; see note) |
| 10 | Does any test or code let grading bypass the test cap or the emergency pause? | **Test cap: no bypass.** Grading reserves against it first and is refused at the cap, through the gateway too, with no ledger row and no provider call. **Pauses:** by the existing P0d design, the global pause (`AI_PAUSED` and the global DB switch) and the school pause stop **non-grading** AI only. Grading continues. P14.2/P14.3 did not introduce this; it is preserved, as the owner's table requires ("preserve existing safety-stop behavior") | VERIFIED_EXISTING; **OPERATOR_ACTION_REQUIRED**: the test-window stop must not rely on `AI_PAUSED` alone (see gate 6) |

**Other checks:**
- **Grading exemption:** institution-level caps never refuse `ai_grading`. The order is ordinary caps, then the grading allowance, then the uncapped, logged emergency overrun. Only `ai_grading` is exempt; tutor, drafting, chat and `ai_grading_proposal` are capped. VERIFIED_EXISTING.
- **User-facing interface:** no screen shows the grading exemption as unlimited. The only "unlimited" text in `frontend/` is a static Enterprise upsell banner in `ManagementDashboard.tsx`. Budget counters are listed only on ENARA-admin routes, and the test counter uses a non-school tenant id (`__test_spend__`), so school views never list it. VERIFIED_EXISTING.
- **Usage ledger:** a known cost has `costStatus` `estimated` (list price) and a positive `costInternal`. An unknown cost is `usage_unknown` with `costInternal: null`, never 0. Unchanged. VERIFIED_EXISTING.

**Note on Railway/Docker (#9):**
- Making `src/index.ts` staging-only would break local development.
- A separate staging start entry for the Docker image would be a new deployment shape for a target that is not in use.
- So it is listed as deferred. If that target is ever used, give it its own staging entry (the same `assertStagingEntry` call) before deploying it.

## Phase 3: tests

**New test files:**

`backend/test/p14_3StagingStartup.test.ts` (13 tests):
- **Migrations on start:**
  - staging never migrates on start (`false`, `FALSE`, ` false`, `False`, unset, `true`), and non-staging is unchanged;
  - the guard accepts `FALSE`;
  - against an in-memory database: staging with `FALSE` connects to `enara_staging_alpha` and runs **no** migration (the migration runner is mocked);
  - control: outside staging the mock does run, which proves the test is live.
- **Paid paths:** each of the 6 paid-path settings without cap+id is refused; with only the cap it is refused; with both it is accepted. No paid path means no cap is needed.
- **Entry points:**
  - exactly one Vercel function, and `api/` holds only `index.js`, which has a single `require` of `dist/vercel.js`;
  - no `backend/vercel.json` or `backend/api/`;
  - in `vercel.ts`, `assertStagingEntry` comes before `getConfig()`, which comes before `createApp()`, and `connectDB()` appears only inside the handler.

`backend/test/p14_3TestSpendEnforcement.test.ts` (8 tests):
- **Concurrency:** 24 concurrent reservations across schools and features; exactly 5 fit the cap; the rest are refused with `AI_TEST_SPEND_CAP`; nothing extra is held.
- **Replays:** a reused key is refused and neither releases nor re-reserves the first attempt, even after settlement.
- **Unsettled reservations:** an in-flight reservation blocks a call that would pass the cap.
- **Failed settlement:** the reservation stays counted, and the sweep turns it into unknown exposure.
- **Retries:** 2 failures + 1 success means 3 reservations. The ledger shows `usage_unknown`, `usage_unknown`, `estimated`, and the counter = 2 × bound (unknown) + actual.
- **Retries cannot pass the cap:** with room for 2 attempts, the 3rd is refused before the provider (provider called exactly twice; 2 `usage_unknown` rows).
- **Global pause:** non-grading is refused and its test reservation is given back. Grading runs, **consumes the same test cap**, and is refused once it is spent.
- **School pause + exhausted school budget + exhausted allowance:** grading still runs (emergency path) but cannot skip the test cap. The refused grading call reaches neither the provider nor the ledger.
